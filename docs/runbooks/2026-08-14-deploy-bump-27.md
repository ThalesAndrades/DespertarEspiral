## A REGRA QUE NÃO PODE SER QUEBRADA

**A migração vai ANTES das funções. Sem exceção.**

Se as funções subirem primeiro, `order_items` não existe: toda confirmação de pagamento tenta ler a tabela, dá 500 e **o pedido fica `pending`**. Pior, a sequência de 500s pode fazer o **Asaas pausar a fila de webhooks** — e aí não basta aplicar a migração, tem que reativar a fila no painel do Asaas.

Ordem: **migração → 4 funções → front**.

## Passo 1 — Aplicar a migração

Arquivo: `supabase/migrations/20260814_000001_order_items.sql`. É **idempotente** (`if not exists` em tudo) — reaplicar não corrompe nada.

**A) OnSpace:** cole o conteúdo do arquivo no SQL editor do painel e execute.

**B) VPS self-hosted:** copie e aplique via psql dentro do container do Postgres.

```bash
scp supabase/migrations/20260814_000001_order_items.sql SEU_HOST:/tmp/
ssh SEU_HOST 'docker exec -i $(docker ps -qf name=postgres) psql -U postgres -d postgres -v ON_ERROR_STOP=1 -f /tmp/20260814_000001_order_items.sql'
```

⚠️ Em `psql` interativo, **sem `commit` a transação faz ROLLBACK** — use o `-f` acima, que roda em autocommit, ou termine com `commit;`.

### Verificar antes de seguir (as quatro têm que responder)

```sql
select to_regclass('public.order_items');                                   -- esperado: public.order_items
select relrowsecurity from pg_class where relname = 'order_items';          -- esperado: t
select indexname from pg_indexes where tablename = 'order_items';           -- esperado: 2 indices + pkey
select policyname from pg_policies where tablename = 'order_items';         -- esperado: order_items_select_own_or_admin
```

Se qualquer uma falhar, **pare aqui**. Nada foi quebrado — o código antigo não conhece `order_items` e segue funcionando.

## Passo 2 — Deployar as QUATRO funções, juntas

São quatro, não três. Todas tocam `order_items`:

1. `checkout-session` — cobra o total e grava os itens
2. `asaas-webhook` — libera no pagamento confirmado
3. `grant-pending-access` — libera quando a aluna cria conta depois
4. `admin-orders` — **é a confirmação manual do admin** (`confirm_payment` e `revoke_access`). ⚠️ Até 14/08 essa função se chamava `sequenzy-webhook`; foi renomeada porque nunca teve relação com o Sequenzy. **Se algum host ainda tiver a pasta `sequenzy-webhook`, apague-a** — o `scp` abaixo copia, mas não remove o que sobrou.

Subir só as três primeiras deixa o buraco aberto: confirmação manual de um pedido com bump entregaria um produto só, **e de forma permanente**, porque marca o pedido como pago e queima o retry do Asaas.

**A) OnSpace:** deploy pelo painel/fluxo que você já usa, as quatro na mesma janela.

**B) VPS self-hosted:** as funções ficam no volume do container `functions` (edge-runtime). Sincronize a pasta e reinicie:

```bash
scp -r supabase/functions/. SEU_HOST:/opt/SEU_STACK/volumes/functions/
ssh SEU_HOST 'cd /opt/SEU_STACK && docker compose restart functions && docker compose logs --tail=40 functions'
```

Nos logs, procure erro de import de `_shared/orderItems.ts` — é o arquivo novo compartilhado pelas quatro.

## Verificação depois de tudo (só leitura)

```sql
-- Pedidos recentes e quantos itens cada um tem.
-- Pedido ANTIGO com 0 itens é o esperado: cai no fallback por orders.product_id.
select o.id, o.status, o.amount, count(oi.id) as itens
  from orders o
  left join order_items oi on oi.order_id = o.id
 where o.created_at > now() - interval '7 days'
 group by 1,2,3
 order by o.created_at desc
 limit 20;
```

O teste que importa nas primeiras horas: **uma compra normal, sem bump, continua liberando acesso**. É isso que o fallback protege.

## Se der errado

A migração é **aditiva** — não altera nem remove nada do que existia. Rollback é voltar as versões anteriores das quatro funções; a tabela pode ficar onde está, sem efeito.

Último recurso, só se quiser mesmo limpar (hoje não perde dado nenhum, porque nenhum pedido de dois itens existe ainda):

```sql
drop table if exists public.order_items;
```

Se o Asaas tiver pausado a fila de webhooks: aplicar a migração **não** basta, reative a fila no painel do Asaas.

## Ainda NÃO faça: virar o bump para `disponivel`

É esse flip que torna pedidos de dois itens possíveis, e três coisas precisam ser resolvidas antes:

1. **Conteúdo real** do "Mapa dos Sentimentos" (vídeo + áudio) entregue pela Sunyan.
2. **E-mail de recuperação de abandono** (`order-recovery`): hoje mostraria o total com bump (R$ 74,90) com link para uma página que soma R$ 47,90 sem re-marcar a caixa. Decisão de produto.
3. **Reembolso/revogação não conhece itens** — "reembolsar um pedido de dois itens" não existe como conceito no sistema.

Recomendado junto: fazer o `checkout-session` devolver o total cobrado na resposta, fechando a última costura entre o que a página mostra e o que o gateway cobra.
